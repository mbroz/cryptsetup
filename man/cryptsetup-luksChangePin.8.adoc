== Name

cryptsetup-luksChangePin - change the HW OPAL User PIN of a LUKS2 device

== SYNOPSIS

*cryptsetup _luksChangePin_ [<options>] <device>*

== DESCRIPTION

Changes the hardware (HW) OPAL User PIN that unlocks the SED OPAL locking range of a LUKS2 device
configured to use OPAL hardware encryption. This command is mostly relevant to OPAL devices configured
in Single User Mode (SUM); see the SUM explanation below.

The OPAL locking range must be locked, which means the device must not be active or mounted during the operation.

The new PIN is first stored in a new (unbound) keyslot.
Only after the new keyslot has been safely written to the LUKS2 metadata is the PIN changed in the OPAL locking range and the new keyslot activated.
If the operation succeeds, all keyslots holding the old PIN are removed and only the new keyslot remains.
Use --new-key-slot to request a specific keyslot number for the new keyslot.

For a two-layer encryption setup, unless --volume-key-reset is specified, this operation does not change the SW layer volume key (media encryption key) and does not affect the encrypted data stored on the device.

*WARNING:* The --volume-key-reset option regenerates the software (dm-crypt) volume key together with the OPAL User PIN.
This is *not* data reencryption: all data stored on the ciphertext device becomes permanently inaccessible.
This option is only meant to be used immediately after an OPAL drive has been handed over by the OPAL Admin authority, before any real data is stored on the device, so that both the OPAL User PIN and the software volume key are replaced at once.

*<options>* can be [--key-file, --keyfile-offset, --keyfile-size, --new-keyfile, --new-keyfile-offset, --new-keyfile-size, --key-description, --new-key-description, --new-key-slot, --token-id, --token-type, --token-only, --new-token-id, --key-size, --iter-time, --pbkdf, --pbkdf-force-iterations, --pbkdf-memory, --pbkdf-parallel, --keyslot-cipher, --keyslot-key-size, --volume-key-file, --volume-key-keyring, --volume-key-reset, --external-tokens-path, --force-password, --header, --disable-locks, --type, --timeout, --verify-passphrase].

== HW OPAL SINGLE USER MODE

An OPAL self-encrypting drive distinguishes two kinds of authority: the *Admin* authority, which provisions the drive and configures its locking ranges, and the per-range *User* authority, which unlocks a specific locking range.
When formatting with HW encryption (see --hw-opal and --hw-opal-only of the cryptsetup _luksFormat_ command), cryptsetup activates the OPAL2 locking range in Single User Mode by default (since version 2.9.0) if the device properly supports it; this behaviour can also be turned off manually with the --disable-sum option of _luksFormat_.

In Single User Mode, a single User authority is granted *sole ownership* of its locking range and the data stored on it.
In particular, only that User authority is allowed to change the range's PIN (the credential of the locking range); the Admin authority's permission to set the User PIN is removed.
Likewise, only that User authority controls the locking state of the range (can lock or unlock it for I/O).
The Admin authority retains only the ability to cryptographically erase (reclaim) the range, which is a destructive operation that also resets the User PIN back to its default.
This is what provides the strong isolation between the Admin and the User: once the drive is in SUM, the Admin can repurpose the range only by destroying its data, and cannot quietly read or replace the User's PIN.

Consider the typical two-step LUKS2 lifecycle.
First, an administrator (acting as the Admin authority) provisions the device, for example:
....
cryptsetup luksFormat --hw-opal /dev/sdX
....
This activates the OPAL locking range in Single User Mode, generates the initial OPAL User PIN, and stores it in a LUKS2 keyslot protected by the first passphrase.
Because the administrator ran _luksFormat_, they know this passphrase and therefore the OPAL User PIN that it protects.
The device is then handed over to the end user.
At this point Single User Mode already grants the user sole ownership of the range, yet the LUKS2 keyslot (and therefore the OPAL User PIN itself) was created by the administrator and is still known to them, so the handover of control is not complete.

Simply changing the LUKS2 passphrase is not enough to finish the handover.
For an OPAL device the keyslot protects the OPAL User PIN (the key programmed into the drive's locking range), so re-wrapping that keyslot with a new passphrase would leave the same PIN in the drive, and the administrator could still unlock the range directly at the hardware level.

_luksChangePin_, run by the user as the second step:
....
cryptsetup luksChangePin /dev/sdX
....
generates a brand-new OPAL User PIN, stores it in a fresh keyslot protected by the user's new passphrase, programs it into the drive's locking range, and then removes the keyslots that held the old PIN.
After this, the administrator's knowledge of the original PIN is worthless: the user holds the only credential that can unlock the range, and the Admin authority is left only with the destructive erase.
Changing the PIN this way neither reformats the device nor re-encrypts the data.

If the device also uses software (dm-crypt) encryption stacked on top of OPAL (formatted with --hw-opal), the --volume-key-reset option regenerates the software volume key together with the OPAL User PIN.
This closes the remaining gap at handover: any volume key material that might have been exposed during provisioning can no longer decrypt data written afterwards.
Because this discards the current volume key, it is destructive to existing data and must be done before any real data is stored on the device.
It cannot be used for OPAL-only devices (--hw-opal-only), which have no separate software volume key.
